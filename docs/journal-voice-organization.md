# Durable final voice organization

Final organization of a saved, closed live recording uses `journal-voice-organization-v1` over the canonical Journal HTTP API. Streaming ASR, live lightweight cleanup, identity resolution and explicit spoken editing commands keep their existing WebSocket path. Imported recording processing and disposable comparison previews keep their existing workflows.

The App saves a task ID, input SHA256 and bounded plan before submission. A plan contains the entire eligible recording, split at manual or non-text boundaries. The server validates the plan, freezes the published prompt policy and persists it before dispatch. Reads are owner-bound; creation and retry additionally require the managed subscription, cloud consent and enabled voice operation. Authenticated cancellation remains available after consent or entitlement ends and includes newer worker progress for that immutable task ID.

`journal_voice_organization_jobs` stores encrypted payloads using the shared payload cipher. Two bounded gateway workers claim jobs by revision and lease, perform one bounded batch, then save the cursor before continuing. Completed batches survive restarts. A lost running lease becomes `uncertain`; only an explicit retry may resubmit that unfinished batch. HTTP disconnection alone does not cancel accepted work. Quota admission happens after the claim, project-cost admission happens before each provider dispatch, and every metered attempt is settled, including a rejected compact result followed by one full-prompt fallback.

Plans are bounded to 2 MiB, 256 sections, 1024 original targets and 60000 unique source characters. Each source fragment is at most 900 characters; at most two bounded preceding output paragraphs are reconsidered. Original styles, source identity and manual boundaries remain authoritative. Results are published only when all sections finish and use the existing validated PolishRevision format.

Simple, identity-confirmed narrative uses a smaller schema and prompt on the approved final model. Unknown participants, identity correction, structured text and explicit structural cues keep the full request. Lite remains the live cleanup model: the synthetic comparison did not establish a reliable latency advantage for final organization. Compact requests do not justify claiming lower end-to-end latency.

Payloads and results expire 24 hours after creation. Maintenance and expired-task reads remove encrypted payloads, including failures and cancellations. Metadata tombstones expire seven days later. Owner erasure deletes the task rows; compare-and-swap updates cannot recreate erased or cancelled tasks. The task table is included in operational queue metrics and patrol.

Verification uses an isolated MySQL instance, deterministic provider fixtures for logic, and explicitly enabled synthetic audio/text against the configured providers for capability checks. The loopback candidate uses an expiring operator grant and a cumulative cost ledger; it does not manufacture an Apple purchase or prove production deployment. Deployment and RC delivery remain separate authorized steps.
