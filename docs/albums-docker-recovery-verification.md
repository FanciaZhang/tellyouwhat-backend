2026-11-04，在现有腾讯云主机上通过已登记的 `platform-test` 生产者完成独立演练。仅使用合成账户和数据；`production` 指校验器的配置范围，未连接正式相册数据库。

8 个场景均通过。正常恢复证明：已删除资源记录不再出现，另一账户的媒体记录保留；已删相册名称清空，账户删除状态重放；恢复库没有有效账户访问入口并保持隔离。失败场景核对具体异常原因，不以任意报错充当通过。

实际 Docker 检查覆盖禁用网络、768 MiB 内存限制、256 进程限制、只读临时客户端凭据挂载及自动移除。原始合成备份文件的摘要在演练前后一致。

使用主机已有不可变镜像 `mysql@sha256:b3b90af2a6552ae30c266fdb7d5dd55f3afb72404bb78d37fe8a23eb857fd3fb`。打包的 97 个源码及 SQL 文件在传入和演练后均核对 SHA-256。第一轮因验证包漏带 `ops_offsite.py` 在导入阶段失败，未创建数据库；补齐依赖后通过，不混入成功记录。

## 顺带修复的租约问题

备份导出子进程现在继承调用者的工作区租约。进程异常退出时，清理器可继续识别仍在导出的活跃资源。新增测试启动真实子进程，核对租约文件描述符；原提交失败，修复后通过。Docker 中的导出客户端也实际检查继承的描述符。

本机定向检查：备份和删除链路 113 项、检查点调用方 17 项、MySQL 历史/当前快照集成 1 项通过。未启用 Docker 配置时另有 1 项明确跳过，不计入真实 Docker 场景结果。

## 服务与清理

演练前后既有 29 个容器的身份、镜像、启动时间及运行状态一致；四个测试 API 均返回 200。共享测试服务仍为 `6ba3f5825eb847993d4230c2de1df68905950ba8`，当前及回退选择未切换。生产者重新确认相同登记项，仅更新验证完成时间；其自动清理没有删除既有容器、文件或镜像。

两个验证目录在证据取回后移除；确认没有活跃挂载和遗留的本次容器。未安装共享恢复工具、迁移业务数据库、修改权限或启用永久清理。

## 复现与边界

`deploy/tencent/albums_recovery_docker_test.py` 需要显式指定已存在的不可变 `ALBUM_RECOVERY_DOCKER_IMAGE` 和私有 `ALBUM_RECOVERY_WORK_ROOT`。共享主机上只能作为现有登记生产者的 `--run` 命令执行。保留同一工作目录可重新取得原租约并回收异常退出的工作区；清理无法确认时保留目录和密钥，不强制删除。

入口完成实际 SQL 恢复验证，不证明最新异地检查点、在线切换、真实用户数据恢复、Apple 登录或 Sandbox 交易。恢复仍为 `quarantined=true`、`latest_checkpoint_proven=false`、`recovery_ready=false`。自动永久清理继续关闭。
