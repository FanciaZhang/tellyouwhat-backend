## 部署前条件

1. 对统一候选的准确提交完成真实 MySQL/Redis 测试、合同生成检查、Swift 合同测试、运维及隔离恢复测试，以及六个服务镜像构建。旧主分支上的独立 PR 验证不能代替本候选验证。
2. 核对 GitHub `production` 环境的配置与当前服务器配置，尤其是手记语音开关、供应商凭据、模型、订阅商品、代理模式和镜像来源。只记录字段是否匹配，不把凭据值写入源码、日志或构建产物。
3. 记录候选完整提交与镜像摘要。按发布授权激活这一候选；保留当前健康版本及配置快照作为回滚来源。数据库迁移必须兼容已有语音版本。
4. 验证内部就绪、公网 TLS、真实 App 的鉴权/权益，以及健康和手记的业务回归。更新生产对应关系后，才能将候选标为已部署。

发布工作流会用 GitHub 保存的配置替换服务器配置；完成一致性核对前，不能直接以旧主分支运行部署。
备份保留、云服务商快照、撤回或删除后的恢复处理仍需独立核对，不能用任务接口到期校验替代物理删除证明。

## 后台尝试预算

每次 Worker 领取任务后，先验证预留归属、设备、金额及有效期。首次调用使用网关预付额度及原始计量窗口；第二、第三次尝试在调用前分别占用当时的日/月 token 额度。重复的同一尝试预留只扣一次，已结算的尝试不能重新使用折减后的额度。

模型调用返回后，独立结算该次尝试：有可靠用量时使用实际值，缺少用量时保留估算；取消、结果写入失败或其他尝试不会清除这一记录。调用前再次检查任务状态、到期和领取租约，供应商请求的 context 不超过任务有效期。Redis 不可用或应答不确定时不开始模型调用；应答不确定的预留保守保留。持续故障仍受原有三次 Worker 领取上限约束，可能使该任务失败，需要由客户端恢复流程重新提交。

旧的纯标记预留缺少归属和计量窗口，不能通过新 Worker 的调用前检查。部署应先停止旧 Worker 领取并处理在途任务，再切换网关与 Worker；不应让旧 Worker 在新候选启用后继续发起未预留的重试。未执行任务的保守预留可保留至原窗口到期，不能伪造旧预留归属或退款。

该控制不修改每日三次成功识别会话规则，也不是整个项目的现金上限。估算 tokens 尚不受供应商输出硬上限约束；结算服务持续失败时仍保留估算，超估算实际用量需要可恢复台账进一步补记。每次尝试的完整长期用量台账、供应商账单对齐、模型输出上限和实际执行并发控制仍需分别验证。
