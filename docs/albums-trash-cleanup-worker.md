# 相册回收站清理调度

2026-11-03：回收站的 30 天清理已接入原有媒体清理后台任务，与六个月到期清理共用持久租约和分页恢复。源码与本机验证完成，尚未部署或启用。

## 规则与保护

- `ALBUM_TRASH_ERASURE_ENABLED` 默认关闭，独立控制已由用户移入云端回收站且达到 30 天的资产。无需当前订阅或 Apple 在线校验，订阅服务故障不会撤销用户已经作出的删除选择。普通 Sandbox 也只按真实回收站期限处理，不用加速订阅到期触发六个月清理。
- 六个月最终截止仍需要 `ALBUM_RETENTION_ERASURE_ENABLED` 及有效的全购买链证明。未来的 30 天回收站期限不能延长该截止；接口的 `restoreUntil` 继续取两者较早时间。续费与首次删除许可的互斥保持有效。
- 已有回收站计划按原授权继续处理。只有尚未获得首次删除许可的订阅到期计划，才可在用户回收站期限已到时转换为回收站计划；保留有效的空键进度和固定版本计划，撤销旧租约，拒绝旧执行者的迟到授权。已获准的订阅到期删除不转换。
- 原件或派生写入未关闭、恢复库仍隔离、账户正在注销、资产已恢复、环境无效或使用旧开发模拟授权时，保留媒体和容量。取消时保留租约与固定计划，重新创建仓库或到期接管后可续跑；删除响应丢失时只重试同一版本，重新确认对象为空后才结算。
- 继续使用同一个 Gateway 后台生命周期与账户级租约，待机不领取，排空取消并等待结束；不新增服务、公共接口或数据库迁移。启用仍依赖上一轮的迁移 `0082`，本轮没有执行它。

用户删除操作入口的 `ALBUM_TRASH_ENABLED` 与后台清理开关独立；打开清理开关不会自动打开 App 操作入口。后台日志只有汇总计数与可用状态，不记录媒体、相册名称或访问凭据。

## 真实 COS 定向验证（2026-11-03）

新增显式运行的 `albums_live` 探针，使用开发桶中的全新随机路径、4 个各 4096 字节的合成版本，以及隔离、仅 Unix socket 可访问的 MySQL。两个原件版本使用 `MAZ_STANDARD_IA`，暂存文件和相邻文件使用 `MAZ_STANDARD`；未调用 Apple、媒体转码或 App 登录、购买接口。

| 验证 | 结果 |
| --- | --- |
| 实际调度与对象删除 | 清除两个原件版本、一个暂存版本及一条未完成分片上传；只有在目标重新列举为空后才结算 |
| 丢失删除回复 | 适配器隐藏一次真实删除成功回复；容量仍保留，重建仓库后重试同一固定版本，最终仅一条删除账本记录，已用/预留容量均为零 |
| 路径边界 | 同前缀的相邻合成文件经过执行器后仍可逐字节读取；最后由创建它的探针单独清除 |
| 清理身份负向检查 | 对新建合成文件的不带版本 DELETE 返回 403；未扩张云权限 |
| 定向适配器回归 | 13 个顶层测试、91 个子用例通过，零跳过；这一组使用受控 HTTP，区别于上面的真实 COS 请求 |

准备、实际执行及收尾三个真实阶段均通过且未跳过。最终三个精确键的版本、删除标记和未完成分片计数均为零；本机测试数据库、测试用户与 MySQL/Redis 进程也已清理。为验证截止与租约，只推进隔离 SQL 夹具的时钟，COS 签名及系统时钟不变。此处“重建仓库”并非杀进程演练。

探针通过 `ALBUM_TRASH_COS_WORKER_PROBE=1` 显式启用，`ALBUM_TRASH_COS_PHASE` 分为 `prepare`、`run`、`process`、`cleanup`、`status` 和只读的 `pending`。同一私有目录的排他锁、不可覆盖的意图/回执负责交接；执行仅接受本轮固定样本的版本和分片。准备中断或写入结果未知时保留意图，不凭空列表或时间流逝推断写入结束，不重复提交未知写入；`pending` 只检查这些精确路径。

先前失败证据同样保留：首次探针遗漏 HTTP 诊断，其精确路径目前列举为空，但写入终止仍未获证明；另一诊断运行明确收到单可用区类型不适用于多可用区桶的 HTTP 400。随后修正测试类型。第一次执行器夹具又因上传授权尚未到期而正确推迟，修正为推进隔离 SQL 时钟后通过。未为通过测试放宽任何生产保护。

上述首次实测没有覆盖真实删除标记；当时内置浏览器不可用，当前身份也正确拒绝创建标记，不能用“标记计数为零”冒充覆盖。详细回执见[首次真实云端验证记录](evidence/albums-trash-cos-worker-2026-11-03.json)。

### 后续补齐真实删除标记

内置浏览器恢复后，在同一开发桶的新随机路径准备另一组合成样本。控制台明确提示多版本删除只生成标记，随后仅对该精确原件键执行此操作；真实 COS 读回确认两个历史低频版本仍完整，并观察到一个非空版本号的删除标记。

同一执行器随后删除这两个原件版本、标记及暂存版本，终止一条未完成分片。测试适配器隐藏一次真实成功删除的回复，重建仓库后只重试同一版本；最终仅一条删除账本记录，已用/预留容量均归零。同前缀的相邻文件经过执行器后仍逐字节一致，随后由创建者单独清理。最后三条精确路径的版本、标记及分片均重新列举为空；控制台开启历史版本列表时也显示零项。

准备、带标记的只读核对、执行和收尾四阶段均通过、零跳过。`ALBUM_TRASH_COS_REQUIRE_MARKER=1` 强制执行前实际存在标记，避免退化为无标记测试。此次没有修改权限、部署、迁移或开启自动清理；仍不代表真实 App 登录、购买、进程强杀、完整注销或历史备份最终擦除验收。证据见[真实标记清理回执](evidence/albums-trash-delete-marker-2026-11-03.json)。

### 后续补齐真实子进程强杀与续跑

新增 `process` 阶段使用全新合成样本：两个低频原件版本、暂存版本、相邻文件各 4096 字节，以及一条已确认写入的分片会话。父进程保留隔离 MySQL 与资源所有权锁，子进程继承该锁；所有子进程退出并回收后，父进程才释放数据库和锁。不会给实际部署的进程发信号。

在终止分片取得终态响应后、删除固定版本取得成功响应后，分别暂停在 SQL 动作确认前。父进程核对持久计划中的当前动作正是该会话或版本、容量仍为 4096、尚无结算凭证，再发出 SIGKILL 并检查实际退出信号。两个新子进程依次重开同一数据库、重试同一会话或固定版本，完成后的第四个子进程再检查无重复操作。

实际 COS 和隔离 MySQL 验证通过：两次 SIGKILL、单条删除凭证、已用与预留容量归零；结算后重启零删除、零终止。相邻文件经过执行器后仍逐字节一致，随后由创建者清理。准备、强杀恢复、收尾三个阶段均开启 race 检查并通过，无跳过；另有 2 个顶层、11 个子用例的连接范围和持久动作检查通过。1021 项仓库源码输入的摘要保持一致；实际执行范围是相册包及所需依赖。

首轮范围检查因测试目录默认权限不满足要求而失败；首轮真实演练又误把仅适用于六个月到期计划的 `started_at` 字段作为回收站断言。已修正测试夹具和断言，没有更改产品清理逻辑或放宽保护；失败证据保留，原组合成资源由创建者精确清理，最终成功使用另一组新资源。两组已知路径均为空，私有 MySQL/Redis、测试数据库、子进程及 Go 临时目录均已收尾。

此验证只强杀 worker 子进程，不覆盖 MySQL/主机崩溃、云请求尚未返回时的中断、完整账户注销或历史备份擦除。隔离 SQL 时钟用于跨过租约，系统时间和 COS 签名不变。没有修改 IAM、部署服务、启用自动清理或分发 App；此前未取得上传回包的独立旧意图仍未结案。[本轮回执](evidence/albums-trash-process-recovery-2026-11-03.json)保存原始证据、源码摘要和失败范围。
